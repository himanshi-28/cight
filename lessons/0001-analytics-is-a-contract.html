Analytics is a contract, not a calculation

Your first CIGHT-003 skill is deciding what a metric means before choosing repository methods or writing Java.

The tangible win

After this ten-minute lesson, you should be able to explain why “success rate” is ambiguous and place each part of the analytics request in the correct application layer.

Start with meaning

Suppose CIght contains 8 successful builds, 2 failed builds, and 10 pending builds. Two formulas are mathematically valid:

All recorded builds: 8 / 20 = 40%

Completed builds: 8 / (8 + 2) = 80%

The computer cannot choose between them. That is a product and domain decision. A backend engineer first writes the metric definition, then makes code implement it.

Put work in the right layer

  1. Controller
  2. Analytics service
  3. Repository
  4. PostgreSQL
  • Controller: owns HTTP routing and the response boundary.
  • Service: owns the success-rate rule and empty-data behavior.
  • Repository: expresses the data operations that the service needs.
  • PostgreSQL: executes COUNT and AVG close to the data.

Fetching every row and looping in Java would produce an answer, but it transfers unnecessary data and lets memory usage grow with table size. Database aggregates return the small result the service actually needs.

Know the null edge

PostgreSQL computes AVG over non-null values. If no non-null durations exist, the aggregate result is null. The repository reports database truth; the service decides what the API should return for that truth.

Your engineering task

Define the denominator of CIght’s success rate in one sentence. Then defend it against the alternative. Do not write repository code until the contract is settled.
