A CI pipeline is an automated reviewer

Before changing CIght's workflow, learn to trace what happens between a Git push and a trustworthy build result.

The tangible win

After ten minutes, you should be able to open CIght's workflow and explain its trigger, runner, steps, failure behavior, and current deployment boundary.

Why CI exists

Without automation, a developer can push code that compiles only on their laptop, breaks tests, or cannot be packaged. Continuous integration, or CI, runs the same agreed checks whenever code changes. It gives the team fast, repeatable evidence about whether a change is safe to integrate.

CI does not prove the software has no bugs.

It proves that the checks encoded in the pipeline passed in a clean environment.

The GitHub Actions hierarchy

  1. Event
  2. Workflow
  3. Job
  4. Runner
  5. Steps
  6. Result
  • Event: something happens, such as a push or pull request.
  • Workflow: the YAML automation stored under .github/workflows.
  • Job: a group of steps that runs on one runner.
  • Runner: the temporary machine executing the job.
  • Step: one command or reusable action, executed in order.
  • Result: success only if every required step succeeds.

CI versus CD

CI builds and tests changes continuously. Continuous delivery keeps a validated release ready for a human-approved deployment. Continuous deployment automatically releases every passing change.

CIght currently performs CI: it tests, packages, and builds a Docker image. It does not yet push that image or deploy it to Render, so calling the current workflow a complete deployment pipeline would be inaccurate.

Your current CIght pipeline

Open .github/workflows/ci.yml. Read it top to bottom as a story:

  1. A push or pull request triggers the workflow.
  2. GitHub creates an Ubuntu runner.
  3. The runner checks out the repository.
  4. It installs Java 21 and enables Maven dependency caching.
  5. The Maven Wrapper compiles, tests, and packages CIght.
  6. Docker verifies that the production image can be built.

If Maven tests fail, the shell command exits non-zero. GitHub marks that step and job failed, and later steps do not run unless explicitly configured otherwise.
